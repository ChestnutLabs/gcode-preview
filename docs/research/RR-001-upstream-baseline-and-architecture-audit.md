### 5.2 Architecture audit (inherited)
- **Language/build:** TypeScript; rollup (ESM + UMD + `.d.ts`); vitest + happy-dom; typedoc → `demo/docs`;
  eslint 8 + prettier; npm workspace-less single package; Firebase-hosted demo.
- **Module map (`src/`):** `gcode-parser.ts`, `interpreter.ts`, `state.ts` (machine-state parsing);
  `job.ts`/`layer.ts`/`path.ts` (inherited toolpath structures ≈ proto-IR); `scene-manager.ts` +
  `extrusion-geometry.ts` + `helpers/*` (Three.js rendering, **tube geometry**); `thumbnail.ts`,
  `build-volume.ts`, `bounding-box.ts`, `indexers.ts`, `dev-gui.ts` (lil-gui).
- **KEY FINDING — no Web Worker.** Grep of `src/` finds **no** `Worker`/`postMessage`/`OffscreenCanvas`:
  the parser runs **on the main thread**. This validates the Master Plan's worker-first requirement and is a
  primary motivation for **E2 (Worker Parser & Large-File Pipeline)**.
- **Capabilities present:** G2/G3 arcs, multi-color/multi-tool, tube geometry, PrusaSlicer thumbnail parsing,
  build-volume rendering (per upstream README + parser).
- **No normalized public `ToolpathIR`** or capability/warning model — the inherited structures are
  render-oriented, motivating **E1 (DD-001)**. Renderer and parser are coupled through these structures,
  motivating the IR replacement seam.
- **Runtime deps:** `three@0.178.0` (MIT), `lil-gui@^0.20.0` (MIT).

### 5.4 Reference-implementation comparison (E0.6 / #15)

The Chestnut engine goals (versioned neutral `ToolpathIR`, worker-based large-file pipeline, IR-decoupled
Three.js renderer, normalized live-progress mapping) were compared against three field-proven G-code viewers
plus the inherited baseline. Rows are from primary sources (source files, `package.json`, `LICENSE`); branches
`main`/`develop` were read live 2026-07-22 (per-file commit SHAs not pinned).

| Engine | Renderer | 2D/3D | Parse on Worker? | Streaming / large-file | Live progress | IR / data model | License |
|---|---|---|---|---|---|---|---|
| **xyz-tools `gcode-preview`** (inherited) | Three.js (tube, G2/G3 arcs) | 3D | **No — main thread** | Whole-file; no streaming/thinning | None built-in | Render-coupled `job`/`layer`/`path`; **no neutral IR** | **MIT** |
| **Sindarius** `@sindarius/gcodeviewer` + **Mainsail** | **Babylon.js** | 3D | **No — main thread** + cooperative yield | Whole-file `split('\n')`; **LOD tiers** (`everyNthRow`, `meshBreakPoint`, voxel/line modes) | **Yes** — `updateFilePosition(virtual_sdcard.file_position − offset)` (**byte offset**) | Babylon meshes; render-coupled, no serialized IR | Viewer `package.json` **LGPL-3.0-or-later** but **no LICENSE file** (`license: null`); Mainsail **GPL-3.0** |
| **Fluidd** | **SVG** | **2D** | **Yes — Web Worker** | **True streaming** (`ReadableStream`+`TextDecoder`) | **Yes** — byte offset → move index; `followProgress` | **`moves`/`layers`/`parts`/`tools`/`bounds`** plain-object model built in worker, decoupled from renderer | **GPL-3.0** |

**Fluidd validates every structural pillar of the Chestnut plan** — worker parsing, streaming/chunked reads,
a renderer-agnostic data model, and byte-offset live mapping — in production. **Sindarius/Mainsail validate
live-position following** (the reference "proven live viewer") but **challenge the worker premise**: they reach
large files entirely on the main thread via LOD + cooperative scheduling, with render-coupled data. Convergent
evidence across two independent mature codebases: **live progress is keyed off the Klipper/Moonraker
`virtual_sdcard.file_position` byte offset** mapped to a line/move index — a strong signal that E5/DD-006 should
accept a **byte offset** as canonical input, resolved to an IR index (exact where an offset→index table exists;
approximate between samples).

**Borrow (behavior specs only) vs. avoid.** Borrow as specs: Fluidd's streaming-worker contract; the
byte-offset→index live-follow contract (with a `followProgress` toggle and a `0..fileSize` scrubber);
Sindarius's LOD/quality tiers as the Three.js large-file degradation policy; feature/role coloring
(extrude/travel/retraction, per-tool color, arcs). Avoid: whole-file main-thread parsing, and coupling the IR
to renderer objects.

**License / provenance (critical): none of the three live viewers are MIT-compatible for code incorporation.**
Fluidd and Mainsail are **GPL-3.0**; the Sindarius viewer declares **LGPL-3.0-or-later** in `package.json` but
ships **no LICENSE file** (GitHub `license: null`), so even that is provenance-weak. Only the inherited
`gcode-preview` is **MIT** and safe to reuse directly. Therefore incorporate **behavior specifications only**,
authored independently; **do not copy source**. Any code lift requires recorded provenance and an explicit
license-compatibility determination; copyleft-derived code is incompatible with the MIT goal.

*(Full research record, with source URLs and per-engine unknowns, was produced for #15; the load-bearing
conclusions — worker/streaming viability, byte-offset live mapping, and copyleft incompatibility — are captured
here. Sindarius's effective license ambiguity is an explicit unknown to resolve before any reuse.)*

### 5.5 Baseline benchmark (E0.5 / #14)

Measured with [`tools/benchmark/parse-bench.mjs`](../../tools/benchmark/parse-bench.mjs): each fixture is
parsed in an **isolated child process** (fresh heap, `--expose-gc`, `--max-old-space-size=6144`), sampling peak
RSS/heap every 50 ms. Environment: **Node v24.16.0**, Windows 11. The engine (`Parser.parseGCode` +
`Interpreter.execute`) is bundled with esbuild from `src/`. This measures **parse + stateful interpretation**
— the exact CPU/memory work E2 moves to a worker. It does **not** measure rendering / first-useful-preview
(WebGL, E3) or scrub/cancellation (no worker exists yet).

| Fixture | Size MB | Read ms | Parse ms | Interpret ms | Total ms | Commands | Points | Peak RSS MB | Peak heap MB |
|---|--:|--:|--:|--:|--:|--:|--:|--:|--:|
| demo/gcodes/mach3.gcode (MIT) | 0.0 | 0.3 | 1.2 | 1.7 | 3.1 | 66 | 20 | 41 | 7 |
| demo/gcodes/easel.gcode (MIT) | 0.0 | 0.4 | 4.4 | 1.8 | 6.6 | 749 | 742 | 43 | 8 |
| demo/gcodes/vase.gcode (MIT) | 0.3 | 1.6 | 39.4 | 12.6 | 53.6 | 11,587 | 7,353 | 54 | 12 |
| demo/gcodes/plant-sign.gcode (MIT) | 0.5 | 2.8 | 72.4 | 20.4 | 95.6 | 22,047 | 12,034 | 66 | 14 |
| demo/gcodes/calicat.gcode (MIT) | 0.6 | 3.0 | 92.8 | 20.5 | 116.3 | 28,636 | 16,407 | 68 | 16 |
| demo/gcodes/screw.gcode (MIT) | 0.7 | 3.0 | 91.0 | 29.3 | 123.3 | 31,393 | 11,683 | 70 | 20 |
| demo/gcodes/3DBenchy.gcode (MIT) | 3.5 | 12.4 | 455.1 | 70.1 | 537.6 | 163,474 | **97,574** | 143 | 60 |
| synthetic ~10 MB (Benchy ×N) | 10.6 | 32.7 | 1,252 | 170 | 1,455 | 490,420 | 292,722 | 286 | 165 |
| synthetic ~100 MB (Benchy ×N) | 102.2 | 296 | 11,143 | 2,972 | 14,411 | 4,740,718 | 2,829,646 | 1,403 | 1,267 |
| synthetic ~250 MB (Benchy ×N) | 250.3 | 668 | 28,062 | 3,688 | 32,418 | 11,606,584 | 6,927,754 | 3,268 | 3,089 |

**Findings (quantified motivations for E1/E2):**
- **Harness validated:** `3DBenchy` yields **97,574** points — identical to the browser demo console.
- **Main-thread parse is a UI-freeze at scale.** Time scales ~linearly (parse ≈ 85–90 % of it): **~1.5 s @ 10 MB,
  ~14.4 s @ 100 MB, ~32.4 s @ 250 MB** — all synchronous on one thread. On the UI thread that is a 14–32 s
  freeze. **Quantifies the E2 worker requirement.**
- **Memory blows up ~13× file size.** The 250 MB file peaks at **~3.27 GB RSS / ~3.09 GB heap** (**11.6 M**
  command objects + **6.9 M** points). Browser/Electron renderer processes commonly cap at ~2–4 GB, so a 250 MB
  parse would **OOM in-browser at default limits**. This is the "millions of reactive JS objects" risk the
  Master Plan flags — **quantifies E1** (compact typed/transferable IR) **and E2** (worker + limits + streaming).
- **Not measurable at baseline:** time-to-first-useful-preview (needs WebGL/E3), and scrub/cancellation
  latency (no worker/streaming yet). Recorded as gaps for the E2/E3 DDs.

## 7. Limitations & accepted unknowns
- **Benchmarks measure parse + interpret only** (§5.5). Time-to-first-useful-preview (WebGL/E3) and
  scrub/cancellation latency (needs a worker/streaming pipeline) are **not** measurable at baseline — targeted
  by the E2/E3 DDs.
- **Large tiers are synthetic** (repetition of `3DBenchy.gcode`): a throughput/memory proxy, not a real 250 MB
  multi-object plate. A real large redistributable plate remains a corpus gap (E0.8/#17); the linear time and
  ~13× memory trends are expected to hold, but absolute numbers on real geometry may differ.
- **Benchmarks were run under Node 24.16.0**, not a browser/Electron renderer; absolute timings/GC differ in a
  V8 browser context, and browser memory caps (~2–4 GB) make the OOM risk *more* acute, not less.
- **Sindarius effective license is ambiguous** (manifest LGPL vs. no LICENSE file) — resolve before any reuse.
- **`alpha` vs `develop` divergence** not diffed in detail (both are the v3 line; assumed close).
- Local Node is 24.x vs CI 22.x; build/typeCheck/lint(LF)/test pass on both.

## 8. Recommendation & rejected alternatives

**Recommended baseline: Candidate A — `develop` @ `15375e56`** (the inherited fork default). **The maintainer
has confirmed this baseline** (active v3 development line, not the older v2 stable or the alpha snapshot). The
inherited vitest-4 test breakage has been **fixed under #23 (PR #24)**, so `dev` is now green and
protected-branch required status checks can be enabled once CI is retargeted to `main`/`dev` (#19).

**Rationale:** A is the most current v3 architecture (tube geometry, latest `three`, active integration line)
and matches Chestnut's worker-based cross-vendor goals. Its only failing gate was an isolated,
confirmed-inherited **test-harness** issue, now resolved without touching product code or downgrading
dependencies. The benchmark evidence (§5.5) confirms A is architecturally the right base to improve: the
main-thread parser and object-heavy model are exactly the seams E1 (typed IR) and E2 (worker) will replace,
and the reference comparison (§5.4) shows a production-proven worker/streaming path (Fluidd) to target.

**Rejected alternatives:**
- **C (v2.18.0 stable):** older v2 architecture; would discard the v3 rework the project intends to build on.
- **B (last-green `9404837`):** green, but pins vitest 3.2.4 and effectively reverts an upstream update we
  would re-adopt anyway; keep as a **fallback** only if the vitest-4 test repair proves unexpectedly large.
- **D (`alpha` tag):** a tagged snapshot of the same v3 line; `develop` (A) is the appropriate *integration*
  base and is already the fork default.
