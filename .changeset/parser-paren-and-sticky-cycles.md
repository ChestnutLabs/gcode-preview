Three parser corrections. A `;` inside a `( … )` comment no longer starts the `;` comment that `onComment` reports: `G1 X1 (a;b) ; real` now reports ` real`, the same split the lexer makes. An unclosed or nested `(` comment now raises one `unbalanced-paren-comment` warning per file (LinuxCNC rejects both; the parse carries on as before, and lines that start with a multi-letter command word such as Klipper `EXCLUDE_OBJECT_START NAME=cube_(1` are not checked). Under `G91`, a canned cycle's `R` and `Z` are now sticky numbers: a later `G81`/`G82`/`G83` block, or a bare `X`/`Y` repeat, that leaves one out applies it again from its own current Z instead of reusing the first block's absolute plane. This differs with `G99` (retract to the R plane), and with `G98` only when the R plane is above the start Z; `G90` cycles are unchanged except for the G98 retract below. A `G98` cycle now retracts to the higher of the start Z and the R plane, as LinuxCNC does (it used to drop back to the start Z even when R was above it). A G91 cycle whose R (or Z) was never given reads it as 0 in the active distance mode, so the R plane is the current Z (the missing-word warning still fires). Lines starting with `M117`, `M118` or `M486` (any case) and with a multi-letter command word keep their parentheses as text: no warning, and `onComment` splits at the first `;` as before. Nothing in the bundled test corpus changes geometry.
