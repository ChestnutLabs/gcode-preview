# Benchmark tools

## `parse-bench.mjs` — inherited parse/interpret baseline (issue #14 / RR-001 §5.5)

Measures the **inherited main-thread parser + interpreter** — `Parser.parseGCode()` +
`Interpreter.execute()` from `src/` — across a corpus of size tiers. This is the CPU/memory work that
Epic **E2** will move to a Web Worker. It does **not** measure rendering / first-useful-preview (needs
WebGL — Epic E3) or scrub/cancellation (no worker exists yet).

```bash
node tools/benchmark/parse-bench.mjs
# optional: write the markdown table to a file
BENCH_OUT=bench.md node tools/benchmark/parse-bench.mjs
```

### How it works
- Bundles a tiny engine entry (`engine-entry.ts`, re-exporting `Parser`/`Interpreter`/`Job`) with **esbuild**
  into a Node-runnable ESM module (the `src/` is written for a bundler, with extensionless imports).
- Benchmarks each fixture in an **isolated child process** (`--expose-gc --max-old-space-size=6144`) so peak
  memory and any out-of-memory outcome are attributed per fixture. Peak RSS/heap are sampled every 50 ms.
- **Corpus:** the seven MIT `test-data/gcodes/*.gcode` fixtures (real) plus synthetic **~10 / 100 / 250 MB** tiers
  generated by repeating `test-data/gcodes/3DBenchy.gcode`.

### Provenance & safety
- Real fixtures are the inherited **MIT** demo files.
- Synthetic tiers are **derived from the MIT demo file, generated to the OS temp dir, and never committed**
  (they are a throughput/memory proxy, not a real large plate — see RR-001 §7).
- No private corpus data is used or produced. Do not point this at `ProjectSource/` files in any committed
  output.

### Requirements
- Node ≥ 22 (developed on 24.16.0). `esbuild` is present via devDependencies.
