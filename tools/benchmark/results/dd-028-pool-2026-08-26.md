# DD-028 geometry worker-pool — measured parallel build (2026-08-26)

Real parallel tube-geometry build via the shipped `GeometryWorkerPool`, driven by a Node
`worker_threads` pool running the shipped `handleGeometryRequest` kernel (the same kernel the browser
Web Worker path uses). Produced by `tools/benchmark/geometry-pool-bench.mjs`.

Machine: maintainer dev workstation (36 host cores; absolute ms are machine-relative — the **speedup
curve** and **byte-identity** are the signal). Input: opossum-scale synthetic, 2.67M segments → 11
extrude tube chunks.

| Build | Time | Speedup | Byte-identical |
|---|---|---|---|
| serial (1 thread, current) | 10,159 ms | 1.00× (baseline) | — |
| pool, 1 worker | 9,868 ms | 1.03× | ✅ |
| pool, 2 workers | 5,235 ms | 1.94× | ✅ |
| pool, 4 workers | 3,077 ms | 3.30× | ✅ |
| pool, 8 workers | 2,059 ms | **4.93×** | ✅ |

## Findings

1. **Near-linear speedup, byte-identical output.** The ~10 s single-thread tube build drops to ~2 s at 8
   workers — a **~5×** reduction — and the geometry is **byte-for-byte identical** to the serial build at
   every worker count (positions/normals/indices/vertexSegment). The main-thread minute the operator sees
   was single-threaded JS; the pool spends the idle cores.
2. **1-worker ≈ serial** (1.03×) — the transfer/orchestration overhead is negligible, so the speedup is
   real parallel work, not measurement noise.
3. **Chunk count caps scaling.** At 2.67M segments the build is 11 chunks, so 8 workers can't perfectly
   balance (some finish early). More/smaller chunks would tighten the curve; the follow-up phase can tune
   the chunk target for the pool. Even so, ~5× at 8 workers is strong.
4. **Bounded by the real core/memory budget in production.** This 36-core box scales freely; a consumer
   is `clamp(hardwareConcurrency − 1, 1, MAX)` (browser) or the **cgroup quota** (Node/sidecar), and the
   memory-aware in-flight cap (the larger phase) keeps peak geometry under budget — so the deployed win is
   bounded by the client's actual cores + memory, not this host's.

## What this proves for DD-028

The self-contained-chunk kernel (RR-008 Phase 1) + the bounded pool deliver a **byte-identical,
near-linear parallel build** with negligible overhead. This is the "measured worker-pool results before
the larger threading phase" gate. The **larger phase** wires the pool into the renderer's build path
(browser Web Worker factory), adds the memory-aware in-flight cap + capability sizing, the cost/capability
activation estimate (shared with `progressivePreview:'auto'`), and the Node/sidecar `worker_threads`
adapter — all against this proven kernel.
